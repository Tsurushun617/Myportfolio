Automation

Claude Codeによる業務の自動化

Journey AI活用の歩み

2025年6月頃

Cursorでコードの一部をAIに任せる

開発中のテーマファイルをCursorに読み込ませ、PHPの繰り返し処理やCSSのスタイリング、HTMLのマークアップなど、コードの一部をAIに書いてもらう使い方から始めました。

2026年5月頃

コードを書くこと自体をAIに任せる

AIの進化に合わせて、使い方を大きく変えました。Claude CodeをFigma MCPなどのツールと接続し、デザインデータを直接読み取らせて実装までAIに任せるようにしています。

現在

人は判断に集中し、AIを業務に組み込む

人が担うのは重要な判断です。何をAIに任せ、何を人が決め、何をAIにやらせないかを整理し、スキルや共通ルールとして業務の流れに組み込んでいます。

Background 取り組んだ背景と課題

日々のWeb制作では、ディレクターからの修正指示の整理、Gitでのブランチ作成やプッシュ、修正前ファイルの控え、テスト環境へ上げるファイルの洗い出しなど、制作そのものではない定型作業が多く発生します。
AIコーディングツールを使い始めた当初は、そのたびに「コードは編集しないで」「プッシュだけでマージはしないで」と同じ指示を書き直しており、指示していない箇所までAIが変更してしまうこともありました。
さらにAIの活用が進むにつれて、トークン（AIの利用量）の上限にすぐ達してしまうことが頻発するようになりました。

そこで、Claude Codeの「スキル（定型業務の手順書）」「サブエージェント（役割を限定したAI）」「フック（特定の操作の直前に自動で動く仕組み）」を組み合わせ、繰り返す作業と守るべきルールを仕組みとして固定しました。作業の難しさに合わせてAIのモデルや考える量（エフォート）を切り替え、品質を落とさずAIの利用コストを抑える設計にしています。

    同じ指示を毎回書き直していた

  • ISSUE 02

    指示していない箇所までAIが変更していた

  • ISSUE 03

    控え・上げ漏れの確認が人の注意力頼みだった

  • ISSUE 04

    トークンの上限にすぐ達していた

Architecture 仕組みの全体像

1つのAIにすべてを任せず、「計画と検収」と「実行」を分けています。メインのAIが依頼を解釈して作業を割り振り、結果を確認してから私に報告します。

Cases 自動化した業務

自分自身やチーム、関わる人の悩みについて、その裏にある根本原因（本質的なボトルネック）を探り、解消する仕組みを考えて実行する。これが私の得意なことです。
ここでは、悩みを「悩み → 根本原因 → 解決 → 成果」の順に整理し、実際に解決してきた事例をご紹介します。

01

修正指示・チェック指摘の解読

  1. 悩み

    • 指示書に曖昧な点や抜け漏れがある
    • 整理の仕方が毎回ばらばら
    • メモの保存場所が統一されていない

  2. 根本原因

    指示を読み解いて残す手順が決まっておらず、毎回その場の判断に任せていた

  3. 解決

    • 曖昧な点を質問リストに整理
    • 修正対象を実際のファイルと照合
    • 方針メモとTODOを日付フォルダに保存
    • この段階ではコードを編集しない

  4. 成果

    • 「指示が来た」の一言で起動
    • 日付ごとのフォルダに同じ形式で残る
    • 追加指示も既存のメモに追記され、誰が見ても経緯を追える

02

Git運用の型化

  1. 悩み

    • Git操作はコマンドやエディターのプラグインで一つずつ行っていた
    • タスクを並行すると、ブランチの作り忘れや作業の上書きが起き、mainへ直接コミットしてしまうおそれもあった
    • コミットやプッシュを忘れて作業を共有できず、パソコンの故障でデータを失ったこともあった
    • 「プッシュだけ」「マージはしないで」と毎回範囲を指定していた
    • 不要なファイルを巻き込むおそれがあった

  2. 根本原因

    Git操作の手順と止めどころが決まっておらず、一つひとつを人の手と記憶に頼っていた

  3. 解決

    • ブランチ作成・コミット・プッシュ・プルリクエストを別々のスキルにし、依頼された工程で必ず止まる設計に
    • mainのまま作業を始めると、変更内容から作業ブランチを作成
    • 「プッシュ」「保存」の一言で、作業途中でもGitHubへ退避
    • 変更内容からコミットメッセージを自動で作成
    • 全ファイルを一括で追加するコマンドを禁止し、機密情報や巨大なファイルの混入を防止

  4. 成果

    • アプリを行き来しなくて済むので集中が途切れない
    • 操作ミスが大幅に減り、作業も明らかに速くなった
    • 並行作業でのブランチの作り忘れや上書き、プッシュ忘れによるデータ消失のリスクを解消
    • コミットメッセージの書き漏れが減少
    • 作業範囲の念押しが9件から2件に減少

03

修正前ファイルの自動バックアップ

  1. 悩み

    • 修正前に原本を控えるルールがある
    • AIへの指示が毎回必要
    • 同じ再指示が4回続いた

  2. 根本原因

    控えを取るかどうかが、AIへの指示と人の記憶しだいだった

  3. 解決

    • ファイル編集の直前に自動で動くフックを作成
    • 原本を日付フォルダへ自動で退避
    • 同じ作業ブランチ内では最初の原本だけを残し、修正前のファイルを特定しやすく

  4. 成果

    • 指示しなくても控えが必ず残る
    • 人の注意力に頼らず、本番反映のミスをいつでも戻せる

04

役割を分けたAIによる品質チェック

  1. 悩み

    • 実装したAI自身の確認では見落としが残りやすい
    • デザインとの細かなズレは目視頼み
    • 文言・リンクの誤りも目視頼み

  2. 根本原因

    実装と確認を同じAIが担い、細かな照合は人の目視に頼っていた

  3. 解決

    • 画面を撮影してデザインカンプと比較
    • 別のAIにコードをレビューさせる
    • 文言とリンクだけを機械的に照合
    • 指摘がなくなるまで繰り返す（上限3巡）

  4. 成果

    • 観点ごとに抜けなく確認できる
    • チェックは依頼したときだけ動くため、品質を担保しつつ、確認の工数と待ち時間をコントロールできる

05

アップロード対象・人の作業の一覧化

  1. 悩み

    • FTPの手動アップロードで上げ漏れが起きやすい
    • 管理画面での設定作業を伝え漏れることがある

  2. 根本原因

    アップロード対象と管理画面の作業を、差分ではなく人の記憶から洗い出していた

  3. 解決

    • Gitの差分からアップロード対象を自動で洗い出し
    • ファイル・カスタムフィールド設定・固定ページ本文など種類別に一覧化
    • アップロードや本番反映は人が行う線引き

  4. 成果

    • 反映前に「何を・どこへ」が一覧で分かる
    • 上げ漏れの確認を差分にもとづいて行える

06

作業の中断と再開

  1. 悩み

    • 作業を終えるたびにTODOの更新を依頼
    • 「次回スムーズに再開できるように」と毎回長い説明が必要

  2. 根本原因

    再開に必要な情報の書き残し方が決まっておらず、毎回説明で補っていた

  3. 解決

    • TODOと方針メモを実態に合わせて更新
    • 「済んだこと／次にやること／人が確認すること」を書き直す手順をスキル化

  4. 成果

    • 引き継ぎの説明が短くなった
    • スキル化後の24件のうち18件は、「今日はここまで」の一言だけで完了

07

作業の難しさに合わせたモデル・エフォートの切り替え

  1. 悩み

    • AIの活用が進むにつれ、トークンの上限にすぐ達するように
    • 複雑な作業を軽いモデルで行うと、意図どおりの成果物にならない
    • 簡単な作業を高性能なモデルで行うと、不要な文脈まで読んでトークンを浪費する

  2. 根本原因

    作業の難しさと、使うモデル・考える量の組み合わせを決めていなかった

  3. 解決

    • スキルごとに、作業の難しさに合ったモデルとエフォートを設定
    • 指示書の解読や本番反映など、ミスが手戻りにつながる作業は考える量を最大に
    • コミットメッセージ作成などの定型作業は、軽量モデルで処理
    • サブエージェントはスキルの中から自動で立ち上がり、軽量モデルで調査・照合して結論だけを返す
    • 長時間の作業の前に、利用枠と作業規模を確認

  4. 成果

    • 作業に見合ったモデルで動くため、成果物の質を保ちながら、AIの利用コストを抑えられる
    • 定型業務はスキルを呼び出すだけで、人が毎回指示しなくても、適切な品質で回る

08

画像の書き出し・圧縮・編集・作成

  1. 悩み

    • Figmaからの画像書き出し（2倍）を1点ずつ手作業で行い、時間がかかっていた
    • 重い画像はWebサービスに1枚ずつアップロードして圧縮していた
    • 書き出した画像の名前や格納場所を毎回手で整えていた
    • ちょっとした加工もデザイナーへの依頼が必要だった

  2. 根本原因

    書き出し・圧縮・命名・加工が、1点ずつの手作業と人への依頼に頼っていた

  3. 解決

    • Figmaのデザインデータから、必要な画像を2倍の解像度でAIが書き出し
    • 重い画像を抽出して圧縮し、AIが圧縮前後を見比べて劣化を確かめる手順をスキル化
    • 画像は内容が分かる名前に変えて適切なフォルダへ格納（何倍で扱うかは実寸を確かめて人が判断）
    • バナーから文字や人物だけを切り出す、ボタンの色を変えるといった加工をAIに依頼
    • 解説記事用の図解など、画像の作成や動画の圧縮もAIに依頼

  4. 成果

    • 時間のかかっていた画像の書き出しから圧縮・加工までをAIに任せられる
    • デザイナーへの画像修正の依頼が大幅に減少
    • 圧縮後の見た目もAIが確かめるため、画質を保ったまま表示速度に配慮できる

09

React / Next.js 学習の仕組み化（出題・採点・復習）

  1. 悩み

    • React / Next.js を独学中で、まずは土台となるJavaScriptの基礎を学び直している
    • AIにコードを書かせるだけでは、AIが書いたコードを読んで正しさを判断する力が育たない
    • 「読めた気がする」は自分では気づきにくく、理解度を客観的に測る手段がなかった
    • テストの結果をターミナルでしか確認できず、見返しにくかった
    • 学習でもAIの利用上限にすぐ達していた

  2. 根本原因

    AIに書かせる学び方では自分でコードを読む機会がなく、理解度を測る物差しもなかった

  3. 解決

    • 学習計画をClaude Codeで自作し、Notionと接続して計画表や成績表を視覚的に管理
    • 基礎を固める期間は、AIの役割を講師と出題役に限定し、コードは自分で打つルールに
    • 節を終えるたびにAIが5問を出題。Notionで答えて「済」と送ると、丸付け・模範解答・図解つきで採点
    • 難易度は教材を読んだ周回と前回の正答率で自動調整（用語 → 認識 → 予測 → 診断の4段階）
    • 同じ項目を2回まちがえたら図入りの解説記事を、記事のあともまちがえたらその項目だけの重点テストを作成。質問への回答も解説記事としてNotionに残す
    • 間隔を空けた復習の研究を参考に、翌学習日・3日後・7日後に出し直す台帳をAIが管理し、毎朝の復習テストと週末のまとめテストで定着を確認
    • 台本から、講師と生徒の2人の音声で進む講義動画を自動で生成し、耳でも復習
    • 利用量の約6割を占めていたNotionへの書き写しは軽量モデルのサブエージェントに任せ、解説や採点の中身は高性能なモデルで作成

  4. 成果

    • つまずきを記録から自動で浮かび上がらせ、何を直すべきかを数字と手順で管理
    • 合格に届かなかった節は再テストに回す
    • 「できた気」ではなく、テストで確認できたことだけを進捗として数える
    • 目指すのは、AIが書いたReactのコードを読んで正しさを判断し、直す指示を出せるエンジニア

Principles 自動化で大切にしていること

01

頼まれた範囲だけ動かす

プッシュ・本番反映・レビューは、依頼があったときだけ実行します。「ついでに」「念のため」で工程を進めないことを仕組みで保証しています。

02

事実と推測を分ける

判断の根拠はデザインカンプ・公式ドキュメント・実際のファイルに置き、裏が取れないことは「未確認」と明記させています。

03

人とAIの境界をはっきりさせる

実機での表示確認や本番への反映など、AIが確かめられない工程は「人が確認すること」として明示的に切り分けます。

04

機密を外に出さない

認証情報や不要なファイルがリポジトリに混入しない操作だけを許可し、うっかりミスが起きにくい状態を保っています。
